# 초보자를 위한 문서 하네스 전체 안내서

이 문서는 Project Combination Engine의 문서 하네스를 처음 접하는 개발자가 각 문서의 역할과 서로의 관계를 한눈에 이해하도록 돕는다.

현재 저장소에는 애플리케이션 구현 코드보다 **무엇을 만들어야 하고, 어떤 규칙을 지켜야 하며, 어떻게 완료를 확인할지 정의한 문서**가 중심으로 들어 있다. 따라서 아래 문서들은 완성된 기능 설명서가 아니라 앞으로 코드를 작성할 때 따라야 하는 설계 기준이다.

## 1. 문서 하네스란 무엇인가

이 프로젝트에서 문서 하네스는 개발 작업을 둘러싼 안전장치다.

- 제품 요구사항은 “무엇을 만들 것인가”를 정한다.
- 기능 명세는 “사용자에게 어떻게 동작해야 하는가”를 정한다.
- 공용 계약은 “화면, 서버, 파일이 같은 데이터를 어떻게 이해할 것인가”를 정한다.
- 보안 문서는 “어떤 데이터를 보호해야 하는가”를 정한다.
- 인수 체크리스트는 “정말 완성되었는가”를 확인한다.
- ADR은 “왜 이 기술 방식을 선택했는가”를 기록한다.

문서끼리 충돌하면 다음 순서로 판단한다.

1. `AGENTS.md`
2. `docs/shared/`의 공용 계약
3. 프론트엔드·백엔드 기능 명세

## 2. 최상위 문서

### `AGENTS.md`

프로젝트 전체에서 가장 우선하는 규칙이다. 제품 목표, 프론트엔드와 백엔드의 필수 기능, 데이터 흐름, 보안 원칙, 구현 원칙, 최종 완료 기준을 모두 담는다.

핵심 내용은 다음과 같다.

- 인재 프로필, 역량, 관계망을 관리하고 시각화한다.
- 프로젝트나 부서별로 여러 네트워크를 독립적으로 관리한다.
- Markdown, JSON, 자연어로 데이터를 가져오고 내보낸다.
- 로그인한 사용자마다 데이터를 완전히 분리한다.
- AI 비밀 키는 서버에서만 관리한다.
- 외부 입력과 AI 결과는 검증한 뒤에만 기존 데이터에 반영한다.
- 기능을 바꾸면 관련 명세와 체크리스트도 함께 바꾼다.
- 오래 영향을 미치는 기술 결정은 ADR로 남긴다.

초보자 관점에서는 **개발 중 어떤 선택을 하더라도 절대 훼손하면 안 되는 프로젝트 헌법**으로 이해하면 된다.

### `docs/README.md`

전체 문서의 안내 지도다. 제품, 프론트엔드, 백엔드, 공용 계약, 품질, 결정 기록, 템플릿 문서가 어디에 있는지 보여준다.

또한 문서 권장 읽기 순서, 기능 변경 시 함께 수정해야 할 문서, 문서 상태의 의미를 설명한다.

- `기준`: 구현이 따라야 하는 확정된 계약
- `초안`: 아직 검토 중인 내용
- `폐기`: 더 이상 사용하지 않는 내용

## 3. 제품 문서

### `docs/product/requirements.md`

사용자 입장에서 제품이 제공해야 할 기능과 품질을 요약한다.

- 인재 추가, 조회, 검색, 태그 필터
- 네 가지 역량의 레이더 차트 표시
- 인물 관계망 탐색과 조작
- Markdown 가져오기·내보내기
- JSON 백업·복원
- 자연어를 AI로 분석한 뒤 사용자 확인을 거쳐 반영
- 여러 네트워크의 생성, 전환, 복제, 삭제
- 회원가입, 로그인, 로그아웃, 프로필과 비밀번호 변경
- 사용자별 데이터 격리, 반응형 화면, 테마, 접근성, 입력 검증, 비밀 보호

특정 디자인 복제, 특정 AI 공급자 고정, 고정 포트, 동시 공동 편집, 외부 조직 인증 연동은 현재 필수 범위가 아니라고 선을 긋는다.

초보자 관점에서는 **기능 목록과 프로젝트 범위를 확인하는 문서**다. 새로운 기능을 만들기 전에 이 문서의 범위에 들어가는지 먼저 확인한다.

## 4. 공용 계약 문서

공용 계약은 프론트엔드, 백엔드, 파일 입출력이 서로 다른 의미로 데이터를 다루는 문제를 막는다.

### `docs/shared/data-model.md`

프로젝트에서 사용하는 핵심 데이터의 의미와 검증 규칙을 정의한다.

- `User`: 고유 사용자 ID, 이메일, 실명, 소속, 직책, 인증 정보
- `Person`: 고유 인물 ID, 이름, 네 가지 역량 점수, 태그, 선택 프로필 정보
- `Competency Stats`: 실행력, 분석 및 연구력, 창업가 성향, 글로벌 역량
- `Connection`: 두 인물의 ID, 관계 강도나 시너지, 선택적인 관계 유형과 출처
- `Network`: 한 사용자에게 속한 네트워크와 그 안의 인재·관계
- `Backup Envelope`: 백업 형식 버전과 네트워크 데이터

특히 사용자 소유권은 이름이나 이메일이 아니라 바뀌지 않는 사용자 ID로 판단하고, 점수 범위·연락처·관계 대상·중복 ID를 검증하도록 요구한다. 비밀번호 원문과 서버 비밀은 일반 데이터나 백업에 포함하지 않는다.

초보자 관점에서는 **타입이나 데이터베이스 스키마를 만들기 전에 읽어야 하는 데이터 설계도**다.

### `docs/shared/data-flow.md`

데이터가 어떤 순서로 이동하고 언제 저장되는지 정의한다.

- 로그인 후 현재 사용자 ID가 확정되어야 그 사용자의 데이터를 읽는다.
- 계정을 바꾸면 이전 사용자의 메모리 상태를 먼저 제거한다.
- 직접 편집은 입력과 소유권을 검증한 후 저장한다.
- 파일 가져오기와 복원은 임시 공간에서 전체 검증한 후 한 번에 반영한다.
- 자연어 분석 결과는 임시 후보로 보여주고 사용자가 승인한 것만 저장한다.
- 검증 실패나 외부 서비스 오류가 기존 데이터를 덮어쓰면 안 된다.

초보자 관점에서는 **사용자 동작부터 저장까지의 처리 순서도**다. 상태 관리 코드를 작성할 때 기준으로 삼는다.

### `docs/shared/import-export-contract.md`

Markdown과 JSON 파일이 어떤 데이터를 담고 어떻게 안전하게 처리되어야 하는지 정한다.

- Markdown은 인물 ID, 이름, 프로필, 네 가지 점수, 태그, 사실·해석·적합도, 관계를 표현한다.
- 내보낸 Markdown을 다시 가져오면 같은 의미의 데이터가 복원되어야 한다.
- JSON 백업은 형식 버전, 사용자의 네트워크, 인재, 관계, 비민감 설정을 포함한다.
- 복원 전에 구조, 버전, 타입, ID 중복, 점수 범위, 관계 대상, 크기를 검증한다.
- 지원하지 않는 미래 버전은 추측해서 읽지 않고 안전하게 거부한다.
- 실패하면 기존 데이터를 그대로 유지한다.

초보자 관점에서는 **파일 형식과 백업·복원 규칙을 정한 약속**이다.

### `docs/shared/security-data-protection.md`

사용자 데이터와 비밀 정보를 보호하는 공통 보안 기준이다.

- 모든 데이터 접근은 현재 사용자의 고유 ID 범위로 제한한다.
- 브라우저 저장소도 사용자별 키 공간을 사용한다.
- AI API 키, 비밀번호, 토큰은 클라이언트·응답·로그·내보내기에 넣지 않는다.
- 브라우저 저장 데이터, 파일, API 요청, AI 응답을 모두 신뢰하지 않고 검증한다.
- 개인정보를 AI에 보낼 때는 사용자가 명시적으로 실행해야 한다.
- AI는 원문에 없는 연락처나 관계를 추측하면 안 된다.
- 오류 응답에 내부 스택, 파일 경로, 자격 증명, 전체 원문을 노출하지 않는다.

초보자 관점에서는 **인증, 저장, 파일, AI 기능을 건드릴 때 반드시 다시 확인해야 하는 보안 체크 기준**이다.

## 5. 프론트엔드 문서

### `docs/frontend/README.md`

프론트엔드 문서의 목차와 공통 규칙을 담는다. 사용자 ID 확인 전 데이터 로드 금지, 외부 입력 검증, 로딩·성공·빈 상태·오류 구분, 키보드 사용, 모바일에서도 기능 유지가 핵심이다.

### `docs/frontend/architecture.md`

프론트엔드가 맡는 책임과 상태 관리 경계를 정한다.

- 인증 상태와 사용자 데이터를 분리한다.
- 계정 전환 시 이전 데이터와 선택 상태를 제거한다.
- 사용자별 저장 공간을 사용하고 손상된 데이터를 부분 병합하지 않는다.
- 목록, 상세, 차트, 그래프가 하나의 정규화된 상태를 함께 사용한다.
- AI 결과는 확인 전까지 임시 상태에 둔다.
- 큰 그래프에서도 화면이 멈추지 않도록 렌더링 비용을 제한한다.

초보자 관점에서는 **화면 컴포넌트와 상태 저장소의 책임을 나누는 큰 구조도**다.

### `docs/frontend/ui-accessibility.md`

반응형 화면, 테마, 사용자 피드백, 키보드와 포커스, 접근 가능한 이름, 법적 안내를 정의한다.

- 모바일과 데스크톱에서 핵심 기능을 모두 제공한다.
- 라이트·다크 테마에서 충분한 대비를 유지한다.
- 색상만으로 오류나 선택 상태를 알리지 않는다.
- 모달은 열릴 때 내부로 포커스를 옮기고, 닫힐 때 원래 버튼으로 돌려준다.
- 모든 주요 기능을 키보드로 사용할 수 있어야 한다.
- 이용약관과 개인정보처리방침을 접근 가능한 모달로 제공한다.

초보자 관점에서는 **화면이 보기 좋을 뿐 아니라 누구나 사용할 수 있게 만드는 기준**이다.

### `docs/frontend/authentication-profile.md`

회원가입, 로그인, 로그아웃, 데모 계정, 프로필 수정, 비밀번호 변경의 동작을 정한다.

- 가입 입력값과 이메일 중복을 검증하고 비밀번호 강도를 알려준다.
- 로그인 실패 메시지는 계정 정보가 노출되지 않게 한다.
- 로그인 성공 후 해당 사용자 데이터만 불러온다.
- 로그아웃과 계정 전환 시 이전 사용자 상태를 지운다.
- 비밀번호 변경은 일반 프로필 수정과 분리하고 재인증한다.
- 비밀번호 원문을 로그나 일반 상태에 남기지 않는다.

브라우저만 사용하는 데모 인증은 실제 운영용 서버 인증과 보안 수준이 다르다는 주의도 포함한다.

### `docs/frontend/people-directory.md`

인재 풀 화면의 목록·카드, 검색, 필터, 인재 추가 모달, 상세 패널 동작을 정의한다.

- 현재 사용자와 현재 네트워크의 인재만 보여준다.
- 이름, 소속, 키워드를 실시간 검색한다.
- 검색과 전문 분야 태그 필터를 함께 적용한다.
- 새 인재의 필수 값, 점수, 연락처, ID 중복을 검증한다.
- 상세 패널은 전체 프로필과 관계를 보여주고 반응형·키보드 동작을 지원한다.
- 네트워크가 바뀌거나 선택 인재가 사라지면 오래된 상세 패널을 닫는다.

### `docs/frontend/competency-visualization.md`

선택한 인재의 네 가지 역량을 레이더 차트로 표시하는 규칙이다.

- 모든 축에 같은 최소·최대 척도를 사용한다.
- 프로필을 바꾸면 차트도 즉시 갱신한다.
- 테마와 화면 크기가 바뀌어도 레이블과 의미가 유지되어야 한다.
- 차트를 볼 수 없는 사용자도 이해하도록 지표명과 숫자를 텍스트로 제공한다.
- 값이 잘못되거나 일부 축이 없으면 임의로 그리지 않고 데이터 오류로 처리한다.

### `docs/frontend/network-graph.md`

인물 노드와 관계선을 물리 기반 그래프로 표현하고 조작하는 규칙이다.

- 선택 노드와 직접 연결된 노드를 강조한다.
- 노드 드래그, 확대·축소, 화면 이동을 지원한다.
- 사용자가 옮긴 위치를 안정적으로 유지할 방법을 제공한다.
- 그래프가 안정되거나 화면을 벗어나면 불필요한 계산을 줄이고 자원을 정리한다.
- 존재하지 않는 인물을 가리키는 관계는 렌더링하지 않는다.
- 네트워크를 전환할 때 이전 선택과 화면 상태가 섞이면 안 된다.
- 그래프 정보의 텍스트 대안과 키보드 조작 방법을 제공한다.

### `docs/frontend/graph-management.md`

여러 프로젝트·부서 네트워크를 생성, 전환, 복제, 삭제하는 규칙이다.

- 생성 시 현재 사용자 범위에서 새 ID를 발급한다.
- 전환 시 선택한 네트워크의 데이터와 화면 상태만 불러온다.
- 복제본은 새 ID를 가지며 원본과 독립적으로 변경된다.
- 삭제는 대상과 복구 불가능성을 알리고 별도로 확인받는다.
- 현재 네트워크 삭제 후에는 다른 안전한 네트워크나 빈 상태를 선택한다.
- 다른 사용자나 다른 네트워크에는 영향을 주지 않는다.

### `docs/frontend/data-studio.md`

Markdown, JSON, 자연어를 이용해 데이터를 교환하는 화면의 동작을 정의한다.

- Markdown은 임시 영역에서 파싱·검증하고 결과를 미리 보여준 뒤 반영한다.
- 내보낸 Markdown은 다시 가져올 수 있어야 한다.
- JSON 복원은 버전, 구조, 크기, 참조 관계를 모두 검사한다.
- 개인정보를 AI로 보내기 전에 안내하고 명시적 실행을 받는다.
- AI 분석 중 중복 제출을 막고 취소와 실패를 처리한다.
- AI 결과는 사실, 해석, 전략적 적합도를 구분해 보여준다.
- 사용자가 승인한 후보만 실제 데이터가 된다.

## 6. 백엔드 문서

### `docs/backend/README.md`

백엔드 문서의 목차와 공통 규칙을 담는다. 외부 입력 검증, 서버 전용 비밀 관리, AI 응답 재검증, 안전하고 일정한 오류 형식, 실행 환경 설정 주입이 핵심이다.

### `docs/backend/architecture.md`

Node.js 서버의 책임, 개발·운영 실행 방식, 설정, 요청 처리 순서를 정의한다.

- 개발 중에는 프론트엔드 개발 서버와 API를 함께 동작시킨다.
- 운영 중에는 빌드된 SPA 정적 파일과 API를 제공한다.
- 일반 화면 경로는 SPA 진입점으로 보내되 잘못된 API 경로는 API 오류로 처리한다.
- 포트, 호스트, 환경, AI 설정은 코드에 고정하지 않고 런타임 설정으로 넣는다.
- 요청은 경로·메서드 확인, 크기 제한, 스키마 검증, 작업 실행, 결과 검증, 응답 변환 순으로 처리한다.

초보자 관점에서는 **서버 요청 한 건이 통과하는 전체 파이프라인**을 설명하는 문서다.

### `docs/backend/natural-language-api.md`

자연어 원문을 인재 후보 배열로 바꾸는 API의 의미 계약이다.

- JSON 객체 안에 비어 있지 않고 허용 크기 이하인 원문을 받는다.
- 잘못된 입력은 AI를 호출하기 전에 거부한다.
- 성공하면 공용 데이터 모델에 맞는 인재, 점수, 태그, 연락처, 사실, 해석, 적합도, 관계 후보를 반환한다.
- 원문에 없는 선택 정보는 만들지 않는다.
- 잘못된 요청, 크기 초과, 설정 누락, AI 장애, 파싱 실패, 스키마 실패, 서버 오류를 구분한다.
- 오류에는 안정된 코드와 안전한 메시지만 담는다.
- 성공 결과도 사용자 승인 전에는 저장하지 않는다.

### `docs/backend/ai-extraction.md`

외부 AI를 어떻게 호출하고 그 결과를 어떻게 믿을 수 있는 데이터로 바꿀지 정의한다.

- 공급자 SDK, 모델, 인증 값은 서버 내부에 감춘다.
- AI 공급자를 바꿔도 공용 API와 데이터 모델은 유지되도록 변환 계층을 둔다.
- 실제 등장 인물과 원문에서 확인되는 정보만 추출한다.
- 사실과 AI의 해석을 구분한다.
- 중복 인물을 함부로 합치지 않는다.
- 가능하면 AI의 구조화 출력 기능을 쓰고, 결과를 서버에서 다시 검증한다.
- ID, 이름, 네 점수, 태그, 연락처, 관계, 항목 수와 출력 크기를 검사한다.
- 일부만 맞는 결과를 부분 반환하지 않고 전체 실패로 처리한다.

초보자 관점에서는 **AI의 답을 그대로 데이터베이스에 넣지 않기 위한 검증 방어선**이다.

### `docs/backend/error-handling.md`

모든 API 오류를 클라이언트가 일관되게 처리하도록 공통 오류 형식을 정한다.

- `code`: 프로그램이 오류 종류를 구분하는 값
- `message`: 사용자에게 보여줄 안전한 설명
- `details`: 필요한 경우에만 제공하는 비민감 검증 정보

입력 오류, 크기 초과, 잘못된 API 경로·메서드, AI 설정 누락, 공급자 장애, AI 출력 오류, 알 수 없는 서버 오류를 구분한다. 로그에는 요청 추적용 ID를 사용할 수 있지만 비밀번호, 키, 토큰, 전체 원문과 전체 AI 응답은 기록하지 않는다. 재시도에는 횟수와 지연 상한을 둔다.

## 7. 품질과 결정 기록

### `docs/quality/acceptance-checklist.md`

기능이 실제로 완성되었다고 판단하는 최종 체크리스트다.

검증 영역은 다음과 같다.

- 계정과 사용자 데이터 격리
- 인재 풀
- 네 가지 역량 시각화
- 네트워크 맵
- 다중 네트워크 관리
- Markdown·JSON 데이터 스튜디오
- 자연어 AI 분석
- 비밀과 개인정보 보안
- 반응형 UI와 접근성
- 개발·운영 서버와 배포 산출물

체크박스가 아직 비어 있다는 것은 실패했다는 뜻이 아니라, **구현과 검증 결과가 아직 기록되지 않았다는 뜻**이다. 코드만 작성하고 끝내지 말고 자동 테스트나 수동 검증 결과까지 확인해야 한다.

### `docs/decisions/README.md`

ADR(Architecture Decision Record)을 언제, 어떻게 작성하는지 설명한다.

데이터 저장, 사용자 격리, 호환성을 깨는 데이터 변경, 인증과 비밀 관리, AI 공급자 경계, 핵심 렌더링·상태·서버 구조, 새 운영 의존성처럼 오래 영향을 주고 되돌리기 어려운 결정을 기록한다.

파일명은 `NNNN-short-title.md` 형식이며 상태는 `제안`, `승인`, `대체`, `폐기` 중 하나다. 과거 결정을 지우지 않고 새 결정 문서와 연결해 변경 이력을 보존한다.

초보자 관점에서는 **팀이 나중에 “왜 이렇게 만들었지?”라는 질문에 답할 수 있게 하는 결정 일지**다.

## 9. 초보 개발자를 위한 실제 사용 순서

새 기능 하나를 구현한다고 가정하면 다음 순서가 안전하다.

1. `AGENTS.md`에서 절대 지켜야 할 원칙을 확인한다.
2. `docs/product/requirements.md`에서 기능의 사용자 가치를 확인한다.
3. 관련 프론트엔드 또는 백엔드 기능 명세를 읽는다.
4. `docs/shared/data-model.md`에서 필요한 데이터 의미를 확인한다.
5. 저장, 파일, AI가 관련되면 데이터 흐름·입출력·보안 계약을 추가로 읽는다.
6. 구현 전에 인수 체크리스트에서 검증해야 할 항목을 찾는다.
7. 코드를 작성하고 정상 흐름뿐 아니라 실패 흐름과 사용자 격리도 테스트한다.
8. 동작이나 계약을 바꿨다면 관련 문서와 체크리스트도 같은 작업에서 갱신한다.
9. 오래 유지될 기술 선택을 했다면 ADR을 작성한다.

예를 들어 “인재 추가”를 만든다면 `people-directory.md`만 읽는 것으로 끝나지 않는다. `data-model.md`의 Person 규칙, `data-flow.md`의 직접 편집 흐름, `security-data-protection.md`의 사용자 격리, `acceptance-checklist.md`의 인재 풀 검증 항목까지 함께 확인해야 한다.

## 10. 개발을 시작하기 전에 아직 결정해야 할 것

문서 하네스는 제품의 의미와 안전 규칙을 잘 정의하지만, 일부 구체적인 구현 선택은 의도적으로 고정하지 않았다.

- 사용할 프론트엔드 프레임워크와 상태 관리 방식
- 실제 운영 인증 방식과 세션 저장 방식
- 브라우저 저장소 또는 서버 데이터베이스 선택
- 점수와 관계 강도의 구체적인 최소·최대 값
- 자기 관계와 중복 관계 허용 정책
- Markdown의 정확한 문법과 JSON 스키마의 구체적 필드명
- 자연어 API의 실제 경로와 요청·응답 필드명
- AI 공급자와 모델
- 목표 그래프 데이터 규모와 성능 기준 수치
- 배포 환경과 운영 방식

이 값들은 임의로 여러 문서에 흩어 쓰지 말고, 구현 전에 관련 명세에서 확정하거나 장기 영향이 크면 ADR로 결정한다.

## 11. 한 문장으로 보는 전체 구조

사용자가 로그인하면 자신의 데이터만 불러오고, 인재와 관계를 탐색·수정·시각화하며, 파일이나 AI에서 들어오는 데이터는 임시 영역에서 완전히 검증하고 사용자가 확인한 뒤에만 저장한다. 이 전 과정에서 비밀번호와 AI 키를 노출하지 않고, 모바일·키보드·다크 테마에서도 핵심 기능을 사용할 수 있어야 한다.
